1. Overview

ℹ️

The Prompt Evaluation Engine compares an expected JSON output (ground truth) against an actual JSON output produced by an AI service. It generates a score from 0–100 and returns a PASS or FAIL verdict. The engine is fully deterministic — no LLMs are used in the evaluation itself.

It evaluates five independent dimensions, each measuring a different quality aspect of the AI output. Scores from all five are combined using configurable weights into a single Final Score.

Dimension Default Weight What it measures
✅ Correctness40%Are field values correct compared to expected?
🔍 Relevance20%Is the overall document semantically similar?
📋 Completeness15%Are all expected fields present?
🔄 Consistency15%Are repeated runs producing similar outputs?
🛡️ Safety10%Does output contain banned / sensitive keywords?

3. Final Score Formula

Final Score (0–100) =
( 0.40 × correctness ← most important: field accuracy
+ 0.20 × relevance ← document-level semantic match
+ 0.15 × completeness ← no missing fields
+ 0.15 × consistency ← stable across repeated runs
+ 0.10 × safety ← no banned keywords ) × 100

All five dimension scores are in the range 0.0 – 1.0. After the weighted sum, the result is multiplied by 100 to produce a score in the range 0 – 100.

⚠️

Weights are configurable per request via the dimension_weights config field. The default weights shown above must sum to exactly 1.0 — the engine validates this at request time and rejects invalid configs.

4. Scoring Dimensions

✅ Correctness 40%

Field-by-field comparison between expected and actual JSON, after flattening. Each field is scored independently (0.0–1.0) based on its data type, then combined using a weighted average.

Supports: boolean, numeric, short string, paragraph text, nested objects, arrays.

weighted average of field scores
🔍 Relevance 20%

Both JSON objects are serialised to flat text strings and compared using TF-IDF vectorisation + cosine similarity. Measures whether the overall documents are topically aligned, independent of field-level correctness.

TF-IDF cosine similarity
📋 Completeness 15%

Counts what fraction of expected fields are present in the actual output. Extra fields in actual (not in expected) are ignored — they do not penalise the score.

Formula: present_fields / expected_fields

field presence ratio
🔄 Consistency 15%

When multiple_outputs are provided (same prompt run N times), measures average pairwise similarity across all output pairs. If only one output is given, returns 1.0 (N/A).

Purpose: Detect non-determinism in the AI service.

avg pairwise TF-IDF cosine
🛡️ Safety 10%

Scans the entire actual output for banned or sensitive keywords (API keys, PII, security terms, injection patterns). Each unique keyword hit deducts 25 points from the safety score, floored at 0.

Formula: max(0, 1.0 − 0.25 × hits)

keyword scan

Correctness is built from individual field scores. Each flattened field is routed to the appropriate scorer based on its data type:

Integer / Float Penalty band scoring 0.0 – 1.0 (piecewise) 1200 vs 1180 → 0.983
Short String

⚠️

bool is checked before numeric in Python because bool is a subtype of int. Without this check, True would be treated as 1 and False as 0 — producing wrong scores on boolean fields.

Correctness Formula

correctness = Σ(field_scorei × weighti) / Σ(weighti)

7. String Scoring — Short vs Paragraph

String fields are routed to different scorers based on their length compared to paragraph_threshold (default: 60 characters):

Field lengthPathScorerWhy
len < 60 [short-string] rapidfuzz token-sort ratio Short labels don't have enough vocabulary for TF-IDF. Fuzzy matching handles typos and capitalisation.
len ≥ 60 [paragraph] Sentence-transformer embeddings (or TF-IDF fallback) Paragraphs need semantic understanding — same meaning with different words should score high.
✅

Identical strings always score 1.0 regardless of length — exact match short-circuits before any scorer is invoked. This is correct behaviour. The [paragraph] label only appears when the texts are genuinely different.

Fuzzy Token-Sort Ratio (rapidfuzz)

Normalises word order first, then computes Levenshtein edit distance:

// Step 1: tokenise and sort alphabetically "food and beverage" → sorted: "and beverage food" "beverage and food" → sorted: "and beverage food" // Step 2: Levenshtein on sorted strings → identical → score = 1.0 // Without sort: score would be ~0.60 due to character position differences

8. How TF-IDF + Cosine Similarity Works

Used for the Relevance dimension, Consistency dimension, and as the fallback for paragraph fields when sentence-transformers is not installed.

Step 1 — TF-IDF Vectorisation

Each document (JSON serialised to text) is converted into a numeric vector where each dimension represents a vocabulary word, weighted by two factors:

FactorWhat it measuresEffect
TF — Term Frequency How often the word appears in this document Words that appear more get higher weight
IDF — Inverse Document Frequency How rare the word is across all documents Words in every document (like "the", "is") get weight → 0
// Example: 2 documents, vocabulary = {fraud, transaction, the, system} // IDF for each word: IDF("the") = log(2/2) = 0.0 // in BOTH docs → killed IDF("fraud") = log(2/2) = 0.0 // in BOTH docs → killed IDF("transaction") = log(2/1) = 0.693 // in ONE doc → survives // Result: only words unique to one document remain non-zero // Words shared by both → zero weight → don't inflate similarity

The engine uses bigrams (ngram_range=(1,2)) — word pairs like "fraud detection" are treated as additional vocabulary dimensions alongside single words. This captures phrase-level meaning that single words miss.

Step 2 — Cosine Similarity

Once both documents are vectors, similarity is the cosine of the angle between them:

cosine_similarity(A, B) = (A · B) / (|A| × |B|)

Where A · B is the dot product (sum of element-wise multiplications) and |A|, |B| are the vector magnitudes.

Cosine valueMeaning
1.0Vectors point in the same direction → identical content
0.7–0.95Highly similar → same topic, mostly shared vocabulary
0.3–0.7Partially similar → related domain
0.0–0.3Low similarity → different topics or heavy synonym use
⚠️

TF-IDF blind spot: If two sentences mean exactly the same thing but share zero content words (e.g. "insufficient funds" vs "balance too low"), TF-IDF cosine scores near 0. This is why sentence-transformer embeddings are used for paragraph fields — they understand meaning rather than vocabulary.

Fallback: TF-IDF + Jaccard + Concept Clusters

When sentence-transformers is not installed, the paragraph scorer uses a three-signal hybrid:

hybrid = 0.45 × tfidf_cosine + 0.35 × jaccard + 0.20 × concept_cluster_score

final = max(tfidf_cosine, hybrid)
SignalWeightWhat it captures
TF-IDF cosine45%Shared vocabulary, phrase overlap
Jaccard (content words)35%Content word overlap after stopword removal
Concept cluster match20%Domain synonym groups (e.g. "declined" ≈ "rejected")

The max() ensures the pure TF-IDF score wins when vocabulary overlap is strong, while the hybrid boosts scores for synonym-heavy paraphrases where TF-IDF alone would score near zero.

10. Critical Fail Rules

Critical fail rules are override checks that force verdict = FAIL regardless of the final score. They are evaluated after all dimension scores are computed.

RuleTrigger conditionConfig
Rule 1
Critical field mismatch		 Any field listed in critical_fields has a score < 1.0 critical_fields: ["fraud", "risk_level"]
Rule 2
Numeric deviation exceeded		 Any numeric field has deviation > numeric_deviation_threshold (default 30%) — score is already 0.0 numeric_deviation_threshold: 0.30
🚨

If a field appears in both critical_fields AND triggers Rule 2, only one CriticalFailReason is recorded (Rule 1 takes precedence). The result is still FAIL — no duplicate entries.

The response includes a critical_fails array explaining exactly which rule fired and why:

"critical_fails": [ { "rule": "critical_field_mismatch:fraud", "field": "fraud", "detail": "Critical field 'fraud' scored 0.0000 — boolean mismatch: expected true, got false" } ]

11. Verdict Logic

The verdict is determined by evaluating three conditions in order. The first condition that matches wins:

1
IF any critical fail rule is triggered FAIL
Score is irrelevant. A critical fail always overrides.
2
ELSE IF final_score ≥ pass_threshold (default 85) PASS
No critical rules triggered, score is above the threshold.
3
ELSE FAIL
No critical rules, but score is below the threshold.
ℹ️

pass_threshold is configurable per request (default 85). Lowering it makes the engine more lenient; raising it stricter. The threshold applies to final_score on the 0–100 scale.

13. Config Reference

FieldTypeDefaultDescription
field_weights dict {} (all 1.0) Per-field importance weights for correctness. Keys are dot-separated paths. E.g. {"fraud": 0.5, "amount": 0.3}
critical_fields list [] Fields that must score 1.0 or verdict is forced to FAIL. E.g. ["fraud", "risk_level"]
paragraph_threshold int 60 Strings longer than this (chars) use semantic embedding scoring. Shorter strings use fuzzy matching.
numeric_deviation_threshold float 0.30 Numeric fields exceeding this fractional deviation (e.g. 0.30 = 30%) score 0.0 and trigger a critical fail.
pass_threshold float 85.0 Minimum final score (0–100) required for PASS verdict. Validated: must be between 0 and 100.
dimension_weights dict correctness 0.40, relevance 0.20, completeness 0.15, consistency 0.15, safety 0.10 Weights for the 5 scoring dimensions. Must contain all 5 keys and sum to exactly 1.0.
banned_keywords list null (uses built-in list) Custom banned keyword list for safety scoring. Pass [] or null to use the engine default.
ℹ️

Built-in banned keywords include: password, secret, api_key, access_token, ssn, credit_card, cvv, hack, exploit, sql injection, drop table, eval(, malware, ransomware, phishing, jailbreak, and others. See evaluator.py → _DEFAULT_BANNED_KEYWORDS for the full list.
